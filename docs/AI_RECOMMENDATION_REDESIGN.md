# AI 중심 추천 재설계

작성일: 2026-11-08
상태: 2026-11-08 구현 완료 (실제 Gemini 응답은 운영자 시연에서 확인 필요)

## 목표
기존 점수 기반 운동 추천과 고정 식사 예시 추천을 사용자 기능에서 제거한다.
AI가 기록과 사용자 조건에 근거해 추천 후보를 만들고, 사용자가 후보별로 선택해 운동 초안 또는 식사 계획에 추가한다.
AI 추천 결과와 당시 입력 요약은 SQLite에 보존하여 앱을 다시 열어도 조회할 수 있다.

## 화면
상단의 식사 기록 / AI 추천 탭은 유지한다.
AI 추천 안에는 새 추천 / 추천 기록 두 화면을 둔다.

새 추천:
- 오늘의 기록 요약, 운동 가능 시간, 피로도, 통증, 추천 조건.
- 전송 동의 후 AI 추천 생성 버튼. 성공 전에는 추천 후보가 없다.
- 결과는 항상 1. 추천할 운동 / 2. 추천할 식사 순서.
- 운동 카드: 종목, 추천 이유, 참고한 기록, 운동 후보 추가 버튼.
- 식사 카드: 식사 이름, 재료, 추천 이유, 식사 후보 추가 버튼.
- 생성 실패는 오류와 다시 요청만 표시한다. 기존 규칙 기반 추천을 AI 결과처럼 대신 표시하지 않는다.

추천 기록:
- 생성 일시, 당시 목표, 추천 개수를 목록으로 표시.
- 상세에서 두 항목의 원문, 후보, 당시 기록 요약과 추가 여부를 확인.
- 과거 후보도 다시 검토하여 추가할 수 있지만 현재 제외 조건으로 재검증한다.
- 저장 결과를 열어보는 행위는 API를 호출하지 않고 요청 횟수를 소비하지 않는다.
- 기록 삭제는 별도 확인 후 실행한다. 이미 추가한 운동/식사 계획은 삭제하지 않는다.

식사 기록:
- 실제 섭취 기록과 별도로 식사 후보 목록을 표시한다.
- 후보에 계획 날짜/끼니를 지정하고 취소하거나 완료 표시할 수 있다.
- 완료 표시만으로 영양 합계에 더하지 않는다. 실제 먹은 음식과 양을 기존 입력 기능으로 기록한다.
- AI가 만든 식사에 가상의 칼로리나 영양 정보를 자동 등록하지 않는다.

## 기존 기능의 제거 범위
- coach.context에서 recommendations.recommend 점수 계산/상위 후보 선정을 제거한다.
- 기존 고정 식사 목록을 순서대로 제안하던 select_meals 기반 추천을 제거한다.
- AI 요청 전 운동/식사 후보 카드와 기존 accept_recommendation 연결을 제거한다.
- 사용 가능한 기구, 제외 운동, 식사 선호, 알레르기 등 사용자 조건과 저장 데이터는 유지한다.
- 조건 검증은 추천 알고리즘과 분리한다. 기구/제외 종목 필터는 후보 순위나 추천 이유를 결정하지 않는다.

## AI 입력
공통: 목표, 운동 수준, 강조 부위, 현재 컨디션, 날짜.
운동: 최근 28일의 종목별 횟수/세트/최근 수행일 요약, 사용 기구, 제외 종목, 현재 초안 종목.
식사: 오늘 기록한 식사 이름과 영양 합계, 기록 건수, 식사 선호, 알레르기, 제외 재료, 조리 시간/기구.
선택 입력: 저장된 키/최근 체중/목표 체중은 사용 여부를 표시한 뒤 전송한다.
전체 원본 DB, API 키, 시연 코드는 모델 입력에 포함하지 않는다.
현재 허용된 운동 카탈로그와 식재료 목록을 함께 보내 등록 가능한 이름/식재료 ID만 사용하게 한다.
제공된 기록만 근거로 사용한다. 기록 부재를 사실로 안내하고, 기록 누락을 영양 결핍으로 해석하지 않는다.

## AI 출력 계약 v2
JSON 구조화 응답을 사용한다. 자유 텍스트에서 종목명을 추출해 버튼을 붙이지 않는다.

```json
{
  "schema_version": 2,
  "exercise_summary": "기록에 근거한 운동 추천 설명",
  "exercises": [
    {"exercise_id": "catalog-id", "reason": "추천 이유", "evidence": "제공된 기록 근거"}
  ],
  "meal_summary": "기록에 근거한 식사 추천 설명",
  "meals": [
    {"name": "식사 이름", "ingredient_ids": ["catalog-id"], "reason": "추천 이유", "evidence": "제공된 기록 근거"}
  ]
}
```

운동/식사는 각각 최대 3개. 후보가 없는 경우 빈 배열과 이유를 반환한다.
제목은 앱이 고정 출력한다. 모델명, 생성 시각, 결과 ID는 서버/앱이 부여하며 모델에 작성시키지 않는다.
서버와 클라이언트 모두 타입·길이·중복·허용 ID를 검증한다.
운동은 기구/제외 종목/현재 초안 및 통증/고피로/시간 제약을 확인한다.
식사는 알려진 식재료만 사용하고 알레르기·제외 재료·식사 선호를 검증한다. 조리 시간/방법은 AI 추정임을 구분한다.
검증에 실패한 후보는 추가할 수 없으며 제외 이유를 표시한다. 알레르기 필터가 실제 제품 첨가물/교차접촉까지 보장하지 않는다.

## 저장 구조
기존 DB에 CREATE TABLE IF NOT EXISTS 마이그레이션으로 추가하고 기존 기록을 보존한다.

ai_recommendations:
- id: UUID 기본 키, 요청 시 생성한 동일 ID로 저장 중복 방지
- created_at: 시간대가 포함된 생성 일시
- model: 실제 서버가 사용한 모델
- schema_version: 2
- context_json: 동의받아 전송한 당시 입력 요약
- result_json: 검증된 구조화 응답

ai_candidate_actions:
- recommendation_id, kind, candidate_id: 원본 후보 연결
- target_id: 운동 초안 항목 또는 식사 계획 ID
- created_at: 추가 일시
- 동일 후보의 이중 클릭/재실행은 같은 추가 작업으로 처리

meal_plans:
- id, recommendation_id, candidate_id
- name, ingredients_json, reason: 원본 삭제와 독립적으로 보존할 스냅샷
- planned_day, mealtime, status(pending/done/cancelled), created_at
- 영양 합계 조회 대상에 포함하지 않음

실제/데모 DB는 현재 분리 방식을 유지한다. 데모 초기화 시 새 테이블도 함께 정리한다.
API 키/사용자 코드는 이 테이블에 저장하지 않는다.

## 추가 동작의 트랜잭션
운동 후보 추가:
1. 저장된 AI 결과에서 해당 후보를 읽고 현재 조건으로 재검증한다.
2. 기존 초안에 같은 운동이 있으면 중복 추가하지 않는다.
3. 기존 초안을 덮어쓰지 않고 미완료 종목으로 추가한다.
4. 세트 입력 시작값은 기존 최근 수행값을 복사하거나 앱 기본값을 사용한다. AI의 처방값으로 오해되지 않게 표시한다.
5. 초안 저장과 후보 추가 이력을 한 SQLite 트랜잭션으로 처리한다.
6. 실제 운동 기록은 사용자가 완료 체크/운동 종료해야 생성된다.

식사 후보 추가:
1. 저장된 AI 후보를 현재 식사 조건으로 재검증한다.
2. 사용자가 날짜와 끼니를 선택한다.
3. 식사 계획과 추가 이력을 한 트랜잭션으로 처리한다.
4. 실제 섭취 기록이나 영양 합계를 자동 수정하지 않는다.

## 요청 및 실패 처리
요청 → 인증/한도 확인 → AI 호출 → 구조/조건 검증 → 응답 → 로컬 저장 → 후보 표시.
버튼 중복 요청을 막고 요청 ID를 서버에서도 추적한다. 같은 요청 ID의 재조회는 재과금/재생성하지 않는다.
성공 답변은 로컬 저장 완료 후 기록 화면에서 조회 가능하다고 표시한다.
저장 실패 시 결과를 세션에 유지하고 저장 재시도만 제공한다. 저장 재시도는 API를 다시 호출하지 않는다.
503/시간 초과 시 새 성공 기록을 만들지 않고, 기존 추천 기록은 계속 조회할 수 있다.
서버 계약 v2와 앱을 함께 배포하며 버전 불일치는 명시적으로 안내한다.

## 구현 순서 및 검증
1. DB 마이그레이션과 추천 기록/식사 계획 저장 구현.
2. 모델 입력을 기록 요약+사용자 제약으로 변경하고 v2 구조화 출력 검증 구현.
3. 기존 규칙 추천 UI 제거, AI 결과 카드와 두 종류의 추가 동작 연결.
4. 추천 기록 조회/삭제, 식사 계획 조회 연결.
5. 자동 시작 서버와 데스크톱 앱 동시 갱신.

필수 검증:
- AI 생성 전 후보 없음, 실패 시 기존 자동 추천이 나타나지 않음.
- 구조 오류/허용되지 않은 종목·재료/알레르기 충돌 후보 추가 차단.
- 새 프로필 조건으로 과거 후보 재검증.
- 운동 추가가 초안만 변경하고 실제 수행 기록은 유지.
- 식사 추가가 계획만 변경하고 섭취 합계는 유지.
- 이중 클릭, 저장 재시도, 재실행에도 중복 없음.
- 앱 재시작 후 이력 보존, 기록 조회 중 API 호출 없음.
- 데모/실제 데이터 분리 및 데모 초기화.


## 구현 상세와 차이
- 카탈로그의 안정된 한글 이름을 종목/식재료 ID로 사용한다. API v2 운동 후보는 name/reason/evidence, 식사는 name/reason/evidence/ingredients/minutes/tools를 반환한다.
- 식재료는 알레르기/선호 조건으로 허용 목록만 구성하며, 기존 8종 식사 예시의 순위/선정은 사용하지 않는다.
- AI 출력에 잘못된 후보가 하나라도 있으면 전체 응답을 거절한다. 검증되지 않은 부분 응답을 저장하지 않는다.
- 선택 입력인 키/체중은 이번 전송에 포함하지 않는다. 식사·운동 기록 요약과 목표/조건을 사용한다.
- 서버는 성공 응답을 비공개 usage.sqlite3의 request_cache에 요청 ID별로 보관한다. 동일 요청 재조회는 현재 남은 한도를 반환하며 새 호출을 하지 않는다. 처리 중 중복은 503으로 거절한다.
- 로컬 저장 실패 시 세션의 답변으로 저장만 재시도한다. 이전 추천 기록 조회는 API 호출을 하지 않는다.
- 과거 운동 추천 추가 전 현재 컨디션 보류 체크와 현재 기구/제외 종목 조건을 확인한다. 과거 결과가 현재 컨디션에 대한 새 추천을 의미하지 않는다.
